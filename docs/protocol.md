# CLP1 RGB 帧协议

电脑端 `constellation_lamp/seriallink.py` 和板端 `firmware/include/frame_protocol.h` 使用同一格式。一个包包含 16 字节头和 `3N` 字节 RGB，均按灯带 DIN 串接编号排列。导线不产生虚拟像素；图连线方向不影响串口字节次序。

| 偏移 | 字节数 | 内容 |
|---|---|---|
| 0 | 4 | ASCII `CLP1` |
| 4 | 4 | uint32 序号，小端 |
| 8 | 2 | uint16 灯珠数 N，小端 |
| 10 | 2 | uint16 负载长度，小端，必须等于 3N |
| 12 | 4 | uint32 负载 CRC32，小端 |
| 16 | 3N | `R0 G0 B0 R1 G1 B1 …` |

CRC 是 IEEE CRC32，与 Python `zlib.crc32(payload)` 相同；头部不计入 CRC。由于负载长度为 uint16，协议上限为 21845 灯；参考固件的静态缓冲上限更低，以配置头的编译检查为准。当前 N=268，一个包 **820 字节**。固件只接收与自身配置灯数吻合的包；CRC/长度/灯数错误不会发布前台帧。

RGB 是灯效完成亮度和 gamma 处理后的最终字节。原生固件按同一电流模型复核，换序 GRB 后由 RMT 发送，不重复应用 gamma 或亮度；已在预算内的 RGB 不再缩放。限流是估算，不能读取实际电流。Arduino 备选采用 FastLED 的独立估算模型。

完整有效帧被发布且 RMT 发送完成后，固件返回 ASCII `OK <sequence>\n`。ACK 表示软件已接受并提交该序号的帧，不能验证实灯颜色、亮度或电源状态。序号不要求连续，允许重复握手帧；发送端按确切序号匹配 ACK，并累积分段串口回复，忽略启动噪声及旧 ACK。

电脑采用逐帧等待 ACK 的发送方式，默认 460800 baud、30 FPS。容量检查包含 UART 8N1 的每字节 10 bit、WS2812 每像素 30 µs、至少 280 µs 的复位保留、ACK 和 15% 调度余量。268 灯的 WS2812 数据约 8.04 ms；不能只按 804 字节和 UART 带宽计算整个链路的可用帧率。参数修改也需满足板端整包超时和有效帧超时。

开始时最多 3 秒重复发送黑屏序号 0，等待固件就绪。参考固件在 `OK 0` 前返回：

```text
INFO CLP1 268 <64位小写场景SHA256> 0
OK 0
```

灯数、紧凑表指纹和模式必须与主机匹配；缺少 INFO、旧映射或脱机模式不会进入彩色播放。指纹包含量化几何、图关系、成员索引和电气串接顺序，灯数相同的反接/排布修改也能检出。它用于一致性检查，不是身份认证。配置中的 `transport.require_device_identity=false` 可显式兼容只返回 ACK 的旧固件；收到错误 INFO 仍拒绝。构建出的 `hardware.json` 同时绑定 `scene.led_count` 和 `scene.sha256`，打开串口前先核对当前源布局。此后时间由显式渲染时间决定；如果主机迟到，丢弃播放截止时间，不排队发送过时画面。每个包都检查 ACK，失败则停止效果输出。

正常结束、Ctrl+C 或异常都尝试发送独立序号的黑屏包并等待 ACK。它与最后尝试的效果序号不同，防止迟到旧 ACK 误报灭灯；最多重试一次，收发有超时，并保留最初的错误。参考固件在 1000 ms 内没有完整有效帧时主动黑屏；坏包和持续乱码不会刷新此计时器。整包超时为 250 ms，包含慢速持续发来的字节。

`--dry-run path.clp` 无硬件地生成确定性帧包文件，并附加黑屏包。`FrameDecoder(expected_count)` 可以分片解析录制文件，检查包数量、序号、CRC 和最后黑屏。正式连接前可用以下命令验证效果和限流参数：

```powershell
python -m constellation_lamp stream --dry-run build/aurora.clp --effect aurora --duration 2
```

估算公式为：`N × idle_led_ma + sum(RGB bytes)/255 × channel_ma`。超出预算时以统一比例缩放所有 RGB 并向下取整，保持色彩比例；预算低于估算待机电流时直接拒绝。示例系数待机 1 mA/灯、满值 20 mA/通道只是可配置估计，应按实际芯片测量修订。
